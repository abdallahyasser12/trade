# Trading engine architecture

## Design principle

The repository keeps one evidence/risk/lifecycle architecture and puts venue-specific behavior below it. Bybit support does not replace the Quant Desk, adaptive strategy, portfolio governor, persistence, reconciliation, lifecycle or research stack.

```text
Simple operator dashboard
        |
        | start/stop/status only
        v
Detached Bybit Demo burn-in service
        |
        +--> Quant-controlled adaptive crypto engine
        |      |
        |      +--> existing strategy / regime router
        |      +--> existing EvidenceQuantScanner / Edge Intelligence
        |      +--> existing lifecycle / degradation supervision
        |      +--> existing portfolio + risk governor
        |      +--> existing execution-quality journal
        |      +--> existing TradeManagementPolicy + hold intelligence
        |
        +--> CryptoBroker / CryptoMarketDataFeed / instrument boundary
               |
               +--> BybitSpotBroker / BybitInstrumentProvider
               +--> BybitSpotDataFeed / public Spot WS
               +--> private Demo WS observer
               +--> REST reconciliation

Legacy/research paths
        +--> AlpacaPaperBroker / AlpacaCryptoDataFeed
        +--> stock paper engine
        +--> historical + walk-forward research
```

## Canonical instruments

Strategies use canonical internal symbols rather than venue string conventions.

Example:

```text
base_asset:       BTC
quote_asset:      USDT
canonical_symbol: BTC/USDT
strategy_symbol:  BTC/USD   (backward-compatible strategy identity)
venue_symbol:     BTCUSDT
venue:            bybit
```

Formatting is centralized. No strategy performs ad-hoc string replacement.

Instrument metadata is read from the venue at runtime and carries tick size, quantity step, minimum order quantity/notional and maximums. Order normalization uses current trusted metadata rather than hardcoded precision.

## Broker boundary

The Bybit Spot broker normalizes account, balance, instrument, order and execution data into internal structures. Strategies never receive Bybit SDK response objects.

Economic-order construction enforces:

```text
category = spot
isLeverage = 0
```

before the network request. There is no normal execution route to a derivative category, leverage toggle, margin-borrowing or short order.

### Deterministic ownership

Bybit `orderLinkId` is generated by a venue-specific deterministic ID function within the provider's length contract. The durable venue ledger maps:

- internal intent ID
- venue
- `orderLinkId`
- Bybit `orderId`
- symbol
- purpose
- attempt
- creation time

A submission timeout is resolved by querying the same deterministic ID. A timeout never causes a blind second economic intent.

## Spot inventory ownership

Bybit Spot wallet balance is not treated as a derivative-style position.

Bot-owned inventory is reconstructed from durable bot entry/exit executions keyed by Bybit execution ID. The broker exposes only this proven quantity to the execution engine.

The sell ceiling is:

```text
min(proven_bot_owned_quantity, currently_available_wallet_quantity)
```

Manual/external holdings above proven quantity remain invisible to bot liquidation. A wallet deficit relative to proven ownership is an uncertainty condition and fails closed.

## Market data

High-frequency decision context uses public Spot WebSocket data for:

- klines
- order book
- recent trades

and REST for historical/backfill/recovery. The feed exposes canonical completed bars and normalized quote/microstructure snapshots.

The WebSocket layer handles authentication where applicable, heartbeat, bounded reconnect/backoff, resubscription, duplicate tolerance, out-of-order events, sequence/gap detection where supported, and REST reconciliation after uncertain disconnects.

Private Demo streams observe order/execution/wallet events. Economic order entry remains REST-based for Demo.

## Quant decision path

The production Bybit entry path remains:

```text
completed causal data
  -> adaptive strategy / regime route
  -> EvidenceQuantScanner
  -> edge/evidence confidence
  -> execution-quality gate
  -> portfolio/risk governor
  -> burn-in overlay (entry count / rolling loss / cooldown)
  -> Bybit Spot broker
```

BTC, ETH and SOL compete globally for capital. A weak signal does not become an order merely because no stronger symbol exists.

The burn-in imposes a maximum entries-per-24h ceiling, not a minimum activity target.

## Post-entry management

The Bybit path deliberately has one policy source: the existing `TradeManagementPolicy` in `quant/exits.py`.

The strategy's legacy ATR `ratchet_stop()` is wrapped to remain inert on this execution path. The parent engine still owns broker order state, persistence, stop/watchdog mechanics, reconciliation and crash recovery.

`BybitTradeManagementExecutor` converts policy instructions into safe broker actions:

- UPDATE_STOP
- PARTIAL_EXIT
- FULL_EXIT

Hold intelligence is supplied by the existing causal `quant/exit_intelligence.py` implementation.

Partial exits preserve residual protection by reducing the live protective quantity before releasing inventory for the market exit, then reconciling actual fills and resizing protection again from broker truth.

## Persistence and restart recovery

`StateStore` remains the execution-engine state database. A separate `BybitStateStore` records venue IDs, idempotent executions, bot-owned inventory, management state and burn-in evidence.

Both SQLite stores use WAL and durable synchronous writes appropriate to economic-intent crash windows.

The engine state database remains authoritative for current protection. The dashboard projects the current stop from `bot_position:*` state into its read model; presentation never changes trading decisions.

## Health model

Health is one of:

- HEALTHY
- DEGRADED
- HALTED

Unknown broker truth, an unprotected bot-owned residual, unrecoverable protection uncertainty or comparable economic-safety failures produce HALTED rather than a green status.

The dashboard shows public/private WS state, clock skew and unprotected quantity directly.

## UI/process boundary

The browser is never the trading loop.

The Streamlit dashboard launches a detached server process and reads persisted state. Closing the browser, a Streamlit rerun, or a frontend restart does not terminate protection or reconciliation.

The production root `/` is the simple Bybit operator UI. The legacy comprehensive research UI is preserved at `/research` and does not become a prerequisite for ordinary operation.

## Live boundary

Bybit Live credentials have separate names, but the current Bybit operator service does not construct a Live broker and exposes no Live selection. A future real-money path would require a separate explicit review, environment gate and acceptance process; the 3–5 day Demo burn-in does not unlock it.
